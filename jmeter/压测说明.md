# TechHub 压测说明

用 JMeter 对后端接口做负载测试,核心目的是**用数据证明阶段二/三的优化效果**(缓存、异步落库、限流、MQ 削峰),产出「优化前后 QPS / RT 对比」。

## 一、压测什么

| 线程组 | 覆盖接口 | 对应的优化点 |
|---|---|---|
| 读接口-缓存热点路径 | 帖子列表 / 帖子详情 / 评论列表 / 通知未读数 | 缓存穿透、击穿、雪崩、缓存一致性 |
| 写接口-幂等/限流/MQ | 点赞 / 发评论 / 收藏 / 关注 | 幂等 upsert、Redis 固定窗口限流、MQ 异步通知 |

每个虚拟用户会**自己登录一次**(Once Only 控制器里注册 + 登录 + 提取 token),之后请求自动带 `Authorization: Bearer <token>`。这样每个线程 = 一个独立用户,避免单用户被限流导致数据失真。

## 二、前置条件

1. 后端已在 `127.0.0.1:8080` 启动,且 MySQL / Redis / RabbitMQ(192.168.100.128)可达。
2. **改两个参数**为数据库真实值,否则会打到不存在的 id:
   - `postCount`(默认 36):`SELECT MAX(id) FROM t_post;`
   - `maxUserId`(默认 10):`SELECT MAX(id) FROM t_user;`
3. 压测前**关闭 SQL 控制台打印**,否则结果严重失真(见「常见问题」)。

## 三、参数一览

参数都定义在 JMX 里的「压测参数」,命令行用 `-J` 覆盖:

| 参数 | 默认 | 含义 |
|---|---|---|
| host | 127.0.0.1 | 后端地址 |
| port | 8080 | 后端端口 |
| readThreads | 100 | 读接口并发线程数 |
| writeThreads | 50 | 写接口并发线程数 |
| rampUp | 10 | 启动时长(秒) |
| loops | 10 | 每线程循环次数 |
| loadPwd | Test123456 | 压测账号密码 |
| postCount | 36 | 帖子 id 随机范围上限 |
| maxUserId | 10 | 关注目标用户 id 上限 |

> 压测账号 `jmeter_read_1..N` / `jmeter_write_1..N` 首次运行会自动注册,之后重复运行会忽略「已存在」错误并直接登录,可反复使用。

## 四、怎么跑

**① 冒烟(1 线程 1 次,确认能通)** —— GUI 打开 `bin\jmeter.bat`,载入 JMX,勾上「察看结果树」,把两个线程组的 `readThreads/writeThreads` 改 1、`loops` 改 1,跑一遍看登录与 token 提取是否正常。

**② 命令行正式压测(推荐,结果更准)** —— 在 JMeter 的 `bin` 目录执行:

```bat
jmeter.bat -n -t D:\MyJavaProject\TechHub\jmeter\TechHub-LoadTest.jmx ^
  -l result.jtl -e -o D:\MyJavaProject\TechHub\jmeter\report
```

覆盖参数:

```bat
jmeter.bat -n -t ... -JreadThreads=200 -JwriteThreads=100 -Jloops=20 ^
  -JpostCount=<你的maxId> -JmaxUserId=<你的maxUid> -l result.jtl -e -o report
```

- `-l result.jtl`:原始结果 CSV;`-e -o report`:生成 HTML 报告。
- `-o` 的目录必须**不存在或为空**,重复跑先删掉。
- 打开 `report/index.html` 看图表;或直接看 `report/statistics.json`。

## 五、怎么读结果

聚合报告 / statistics.json 里重点看:

- **throughput**:吞吐,即 QPS,是「优化前后对比」的核心数字。
- **meanResTime / medianResTime**:平均 / 中位响应时间。
- **pct3ResTime**:P99(99% 请求的响应时间)。
- **errorPct**:错误率。写接口触发限流会返回 `"code":429`(HTTP 仍是 200,不算 HTTP 错误);读接口有断言,校验响应体含 `"code":200`。

## 六、常见问题

1. **读接口全报错(errorPct=100%)**:确认断言「响应字段」是 `Response Data`(已修复)。若不是,断言在拿「采样器名称」去匹配 `"code":200`,必然全失败——这是假失败,不代表接口真的挂了。
2. **响应时间虚高(1~4 秒)**:多半是 `application.yml` 里 `log-impl: StdOutImpl` 把每条 SQL 打到控制台。压测前改掉或注释,否则控制台 I/O 会成为最大瓶颈。
3. **想验证限流**:点赞/收藏限流是 30 次/分钟、评论 10 次/分钟(按用户)。默认 `loops=10` 通常不够触发,把 `loops` 调大或 `writeThreads` 调小,让单用户请求频率超过阈值即可看到 `"code":429`。
4. **想要干净的吞吐数字**:压测机和后端分开放(JMeter 本身吃 CPU),并调大 HikariCP 连接池(默认 10,150 线程会排队等连接)。

## 七、做「优化前后」对比

1. 先跑当前(已优化)版本,记下各接口 QPS / 平均 RT / P99。
2. 为证明优化有效,可临时关闭缓存(详情走 DB)、关掉异步落库,再跑一次对比——或直接把这版作为「优化后」,配合代码注释讲解即可。
