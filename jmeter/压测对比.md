## 三、结论:优化点在哪、不在哪

### ✅ 真正的收益在「长尾」,不在「平均」

关 SQL 打印 + 调大 HikariCP 连接池,砍掉的不是每条请求的固定成本,而是高并发下**排队等连接 / 控制台 I/O 造成的偶发尖峰**。证据:

- **P99 从 10.8s 掉到 6.1s(-44%)**,读接口 P99 普遍 -40% 左右。
- 平均 RT 只降 9%,但「最慢的 1% 请求」大幅变快——这正是「优化后更稳、更抗毛刺」的体现,面试里比平均 RT 更有说服力。

### ⚠️ 平均 RT 只降 9% 的原因:瓶颈已转移到远程 VM

MySQL / Redis / RabbitMQ 都在 `192.168.100.128`,每个请求多次跨网络往返,这个**固定网络延迟**是关 SQL 打印、调连接池都动不了的。现在 ~2s 的平均 RT 基本是「网络往返 + DB commit」的下限,不是代码问题。

### ⚠️ 写接口(点赞/收藏)P99 略升是正常的

读接口变快后,单位时间打到 DB/MQ 的压力更集中,加上 JMeter 与后端同机抢 CPU,写接口出现一点噪声属正常范围。想拿干净数字需把压测机分开放。

## 四、想继续往上压,就两条

1. **把 MySQL/Redis/RabbitMQ 挪到本机**(或后端与 JMeter 分机),消除网络往返 → 平均 RT 才会真正降下来。
2. 单独验证限流:把 `loops` 调大,让单用户超阈值,观察 `"code":429` 出现。

## 五、一句话总结(面试口播版)

> 优化前 150 并发下总吞吐 53 QPS、P99 超过 10 秒;关掉 MyBatis SQL 控制台打印、把 HikariCP 连接池从默认 10 调到 50 之后,总吞吐提升 14% 到 61 QPS,P99 下降 44% 到 6 秒,错误率归零。剩余 ~2 秒平均响应主要来自远程 MySQL/Redis/MQ 的网络往返,属环境下限,不是业务瓶颈。
